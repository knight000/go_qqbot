# 插件跑在独立进程里，契约外置为 pkg/host

P1（编译期注册）用到现在暴露出三条硬代价，而它们都指向同一个需求——插件要能独立升级：**加一个插件必须重编译核心**（`plugins_gen.go` 是生成物、不入库，克隆后忘了 `go generate` 就得到一份"编译通过但插件不存在"的二进制）；**插件更新等于核心更新**（所有插件与核心共用一个 git tag、一个发布节奏）；**第三方无法独立发版**（`internal/host` 不可跨 module 引用，插件只能以嵌套克隆的形式活在核心仓里，且不能有 `go.mod`）。

`/upgrade` 要做成"一键"，就必须有可独立替换的插件产物。而 Go 侧三条路里，`.so`（`plugin` 包）在 Windows 上根本没有实现、要求工具链与依赖图完全一致、不能卸载、panic 直接打穿宿主；WASM 的收益（真沙箱、可热卸）是真的，但 Go 的 `wasmexport` 太新、TinyGo 的 `reflect`/`encoding/json` 有缺口，而现有契约是强类型 Go 接口，落到 wasm 上等于重设计一套 ABI。剩下唯一成立的是 **P3：子进程 + JSON-RPC**——§3.1 早就把它写成"可增量叠加"的那条路。

本 ADR 定的是：核心变成**宿主**，插件变成**独立可执行文件**，两者之间走长度前缀 JSON 的 stdio 通道；契约从 `internal/host` 外置为 `pkg/host`，插件独立成 module 并直接依赖核心 module。核心只依赖 `[]host.Plugin` 这一个接口，所以路由、权限、调度、会话、渲染一行都不用改——子进程只是一个 proxy 实现。

## 决策

1. **契约外置为 `pkg/host`，插件独立成 module，直接 `require github.com/knight000/go_qqbot`。** 不另立瘦 SDK module：`APIVersion` 是刻意设计的**唯一**兼容性数字，再加一个 SDK 版本号就会出现"SDK 兼容、`APIVersion` 不兼容"这种必须两头核对的组合状态。代价是插件的 module 缓存会拉进核心的依赖与 6 个 TTF（20 MB 上下），但编译只编真正 import 的包，且缓存里只躺一份——这个代价换一个版本号，值。

   `pkg/host` 只放契约类型、哨兵与常量，**不得 import 任何实现包**（尤其不能为了复用而 import `internal/core` 或 `internal/render`）。这条约束现在是编译期的，P3 之后是**线协议**的，破坏它等于把一个实现细节永久烧进跨进程格式。

2. **插件二进制由核心 spawn，不用独立 systemd unit。** 服务账号通常没有 `systemctl` 权限，而一键升级要求核心能"换掉文件 → 拉起新进程"。独立 unit 还会把"重启机器人"和"重启插件"变成两套编排，失败时要同时看两份日志。（插件即 HTTP 服务的形态在 Considered Options 里单独说明。）

3. **核心侧只有一个 proxy 实现 `host.Plugin`。** `host.Plugin` 只有三个必选方法——`Manifest` / `Init` / `Handle`——加三个可选接口 `Starter` / `Closer` / `JobRunner`。proxy 把它们一一转发 RPC，`Manifest()` 返回装配期探测到的缓存值，不每次过通道。**这是本方案最省的地方**：核心的路由、权限、会话接管、调度、渲染全都不认识"进程"这个概念。

4. **传输是 stdio + 长度前缀帧，不是行分隔。** 行分隔在 1–3 MB 的 `Renderer.Markdown` 返回值上会让缓冲区策略变得别扭；长度前缀让每次读都是"先读 4 字节、再读 N 字节"，没有转义问题。请求是 `{id, method, params}` 多路复用，因此 `Session.Await` 这种长请求不会堵住同一插件的其他调用。插件的 stderr 由核心按行抓取、加 `plugin=<name>` 前缀后重放进 `slog`，插件日志不过 RPC。

5. **Manifest 靠 `bin --manifest` 探测，在装配期完成。** 2 秒超时，输出 JSON，然后复用现有的全部启动期校验：`api_version` 与核心一致、`intents` 可解析、每个 `Command` 恰好 Prefix 或 Pattern 之一、正则可编译、前缀不占核心保留词、`config_schema` 的键在 `[plugins.<name>]` 里存在且类型相符。探测失败 = 该插件不加载，记一条 Error；**不 fail-fast 整个启动**（理由见决策 6）。

6. **`api_version` 不匹配 → 拒绝加载该插件，核心照常运行。** 这与 `config_schema` 缺失的 fail-fast 是**刻意不同**的处置：配置写错是人改一下文件的事，插件产物过期是一条网络命令的事；为一个过期插件让机器人整体下线，还会进 systemd 重启循环白烧 Identify 配额（1000/天），代价远大于收益。装载失败必须写进启动日志的插件清单与 bootnotice 的上线报告——否则表现就是"某个指令没反应"，且没有任何线索。

7. **超时由 RPC 层强制，沿用现有口径。** `Handle` 3 秒（`dispatch.go:72` 的 `handlerTimeout`）、`Job` 60 秒（`scheduler.go:122`）。超时即取消该请求并把该次调用记为失败；连续超时与崩溃共用同一套熔断计数。不设"更宽松的跨进程超时"——进程边界不该成为放宽语义的理由，否则最慢的那个插件会拖垮整个 per-peer 队列。

8. **崩溃策略：退避重启 + 熔断。** 子进程非零退出 → 按 1/2/4/8/16 分钟重启，连败 5 次停用该插件并私聊 owner；核心继续跑。这与现有 job 熔断的口径一致。让核心跟随退出等于把 P3 的隔离收益还回去。

9. **错误跨进程只走码，不走字符串。** `{code, status, msg}`：`host` 的每个哨兵有一个稳定数值码，`HTTPStatusError` 带 `status`，两边各自还原成本地哨兵，`errors.Is` 在插件侧照常可用。§3.3 已经明写错误串"只供排障、不得解析"，所以把 `err.Error()` 塞进通道再在对面匹配前缀是明确禁止的做法。

10. **四个内置插件全部迁出。** 它们本来就是示例（echo / adminping / bootnotice / md），没有"随核心版本走"的正当理由。`cmd/bot` 的四个 blank import、`//go:generate`、`tools/genplugins`、`plugins_gen.go` 一并删除——顺带消灭"克隆后忘了 generate 导致插件静默缺失"这个已经踩过两次的坑（`git worktree` 出来的工作区必现）。

    代价要认：核心二进制从此**不自带任何插件**，`/ping`（adminping）与启动私聊报告（bootnotice）都成了插件。它们装上之前，群里没有确认服务存活的手段（核心指令 `/reload` `/reset` `/group` 仍在，但都要管理员权限，且不能证明业务链路是通的）。

11. **出厂态靠 `go:embed`，运行期事实源是文件。** 插件二进制按 `internal/pluginbundle/dist/<os>_<arch>/` 嵌进核心 exe，`qqbot init` 释放到 `<datadir>/plugins/bin/`。**内嵌副本不参与运行期判定**：启动时只扫 `plugins/bin/`，文件在就是装着，不在就是没装。这条边界必须写进文档，否则半年后会出现"插件是编死的"这种误解。

    路径落在 `internal/pluginbundle/dist/` 而不是仓库根的 `dist/`：`//go:embed` 的模式不得引用包目录之外的文件，把产物放包目录里是唯一可行的位置（`tools/build` 与 `//go:embed` 指令同住这个约定）。

    代价有两个，都要认：核心 19 MB → 40 MB 上下（每个插件 4–6 MB 估）；`go build` 前必须先把插件编到 `internal/pluginbundle/dist/<os>_<arch>/`，否则 `//go:embed` 直接编译失败——这跟刚删掉的 `genplugins` 是同一类构建顺序坑，只是从"忘了 generate"变成"忘了先编插件"。

12. **缺失不自动恢复，删除是合法的卸载手段。** 启动期不自愈：`plugins/bin/<name>` 被删掉就是这个插件不存在，不该在下次启动时又冒出来。恢复用显式命令 `qqbot init --plugins`（只释放缺失的插件，不碰配置）。误删的表现必须是**日志里少一个插件名**，而不是"某个指令没反应却查不到原因"。

13. **停用开关在核心侧：`[plugins].disabled = ["echo"]`。** P3 之后"是否启动这个进程"必须由核心决定——插件自己在 `Init` 里读 `[plugins.<name>].enabled` 时进程已经起来了，管不了这件事。两者语义不冲突：`disabled` 是"装而不跑"（临时停用、避开崩溃循环、保留产物），`[plugins.<name>].enabled` 仍是插件自己的功能开关。

14. **Job 注册表留在核心。** 插件的 `Host.Scheduler` 调用仍然只登记 `JobSpec`，per-peer 实例展开、`DueJobs` 的 `left_at=0` 过滤、熔断计数、`/reset` R2 清该群 `job_runs` 全部照旧——这些语义不因为执行体换了进程而改变。跨进程只多一跳"到点了调 `RunJob`"。

15. **契约版本 = 12。** `Host` 从"编译期接口"变成"线协议"，方括号里的兼容性语义变了：11 及以前，不匹配是编译错误；12 起，不匹配是运行期握手拒绝。版本表与 `TestAPIVersionMatchesArchitectureTable` 一起更新。

## 插件目录与握手

```text
<datadir>/plugins/bin/
  echo        # 文件名只是给人看的
  torn
```

启动顺序：扫目录 → 对每个可执行文件跑 `--manifest`（2 秒超时，并行） → 校验 → 跳过 `[plugins].disabled` 里的名字 → 起子进程 → 发 `init`（带 `[plugins.<name>]` 的原始 map） → 进入可路由状态。

不引入 `index.json` 来做"本地该有哪些插件"的判定：本地的事实源就是目录里的文件，索引只在**比对远端版本**时使用（ADR-0006）。

## Considered Options

- **Go `plugin` 包（`.so`）**：Windows 上没有实现；要求 Go 版本与所有共享依赖完全一致，实际等于"必须用同一次构建产出"；不能卸载；插件 panic 直接带崩宿主。四条里任意一条就够否决。
- **WASM（wazero / Extism）**：真沙箱、内存上限、可即时热卸，长期看是最优解。但现在要重设计一套 ABI（`host` 是强类型 Go 接口），TinyGo 对 `reflect` 与 `encoding/json` 的支持有缺口，且插件作者必须换工具链。收益属于"插件来自不可信第三方"的场景，当前不存在这个场景。
- **插件即 HTTP 服务（核心 POST 事件、插件返回动作）**：省掉进程管理与帧协议，插件可以用任何语言写，升级就是 `systemctl restart`。否决理由是升级通道：服务账号没有 `systemctl` 权限，一键升级反而要人工介入；而且双向通道（`SendActive` 中途发消息、`Session.Await` 等待下一条）只能靠轮询表达，会把简单的事做复杂。
- **插件与核心同 module（保持嵌套克隆）**：零迁移成本，`internal/host` 继续可用。但"独立产物"就名不副实——插件没有自己的 module 边界、没有独立版本、第三方进不来。迁移 `internal/host` → `pkg/host` 是机械改动（import 路径 + 版本表），现在做比以后做便宜。
- **独立 SDK module（`sdk/go.mod`）**：依赖图干净，插件不用拉 20 MB 字体。但要维护第二套版本号并与 `APIVersion` 手工对齐，等于给"兼容性"造两个事实源。否决。
- **独立 systemd unit 托管插件**：隔离更强、重启策略独立。但升级要走 `systemctl`（权限）且两套编排，与"一键"直接冲突。否决。
- **启动期自愈（发现文件缺失就从内嵌副本释放）**：能把误删变成无害。但它取消了"删除即卸载"这个语义，用户无法通过删文件去掉一个不想要的示例插件。改成显式 `init --plugins`，把决定权交回人。
- **把 `[plugins.<name>].enabled` 提到核心侧**：不新增配置项。但那是插件的功能开关，语义是"不发消息"而不是"不启动"；混用会让"停用"这件事同时有两种含义，排查时无法区分。

## Consequences

**正面**：插件可单插件热升级，核心不动；插件崩溃不再带崩核心；加插件不需要重编译，也不需要 Go 工具链；契约边界从"约定"变成"进程边界"，插件真要用别的东西必须先改 `host`（这是插件化能否长期成立的关键）；`plugins_gen.go` 那套生成机制和它的坑一起消失；`APIVersion` 从编译期错误变成可观测的运行期状态（启动报告里能直接看到"哪个插件因版本不匹配没装"）。

**代价（都要认）**：

- **约 30 个 RPC 方法。** `host.Plugin` 只有 6 个方法，工程量全在 `Host` 那 13 个访问器背后的子接口上。这是本方案的主要实现成本，也是主要出错面。
- **每条消息多一次进程跳转与序列化。** 延迟量级是亚毫秒，对聊天机器人无意义；但它把"一个函数调用"变成"一次可能失败的 IPC"，失败路径必须逐条想清楚（超时、半包、对端已死、重启中）。
- **新的故障类**：僵死子进程、孤儿进程、Windows 上杀不掉的子进程。核心必须有"发 close → 等 → SIGTERM → 等 → Kill"的三级关闭，且 `/reload` 与关停都要走完这一套。
- **二进制 40 MB 上下**，下载与磁盘占用都变大；Windows 上内嵌的可执行文件被释放到磁盘时，杀软扫描会让首次 `init` 变慢，个别环境下会拦。
- **调试从"一个调用栈"变成"两个进程的日志"**。stderr 转发与 `plugin=` 前缀是必须的，否则排障体验会明显劣化。
- **`api_version` 不匹配从编译期错误退化为运行期错误**。决策 6 的"拒绝加载 + 写进启动报告"是这个退化的补偿，但它终究比编译不过要晚暴露。
- **额外的常驻内存**：每个插件进程 5–15 MB（§3.1 的量化）。

## 本 ADR 不做

- **插件市场的发现与安装**：`init` 只释放内嵌的出厂插件，安装第三方插件靠手工放文件或 `/upgrade plugin`（ADR-0006）。
- **插件配置热更新**：子进程重启时拿到的仍是核心启动时加载的配置快照。改 `[plugins.<name>]` 仍需 `/reload`——两套配置生命周期会比一套难查得多。
- **跨插件的进程复用**（一个进程装多个插件）：当前每个产物一个进程，隔离粒度就是插件粒度。
- **WASM 运行时**：契约外置后这条门是开着的，但不在本次范围。
- **多实例/分片下的插件进程编排**：仍由单实例锁保证只有一个核心进程（§2.1）。
