# 出站配额的记账主体是 owner，窗口用滑动窗口

业务插件（首个是 Torn）要访问的上游 API 按 **owner** 与**出口 IP** 两条口径限流，而进程里的出站客户端只回答「本机每秒能发多快」。这两件事此前在 `ARCHITECTURE.md §6` 里被写成一条「按 key 的令牌桶」，照它实现会同时犯三个错：同一个 owner 配两把 key 会放出两倍额度、令牌桶在窗口边界能放出接近两倍、把官方口径（每出口 IP 1000/min）误当成本地自设的总闸。

本 ADR 固定三条不可逆决策：

1. **配额主体是 owner，不是 key。** 官方按 owner 计（100 次/分钟，跨该 owner 的全部 key 共享）。本地取 95 留余量；429 才是事实来源，本地窗口只是保守估计。
2. **两级滑动窗口，一次授予。** owner 与出口 IP 两个维度在同一个临界区内同时判定并记录，不允许先占一个再占另一个——否则其中一个维度拒绝时，另一个维度已经被无谓消耗。
3. **业务配额与出站限流是两层。** 业务配额约束上游额度，按 owner / IP 记账，实现在插件里（密钥也属于插件配置段）；出站限流约束本机出站速率，按域名分桶，实现在核心 `httpx`。把域名额度做进出站层是通用能力；做进业务插件则每个插件各自限流，且无法阻止别的插件绕过。

## Considered Options

- **按 key 记账**：实现最直接，但同一个 owner 配两把 key 就是两份额度，上游会先打回 429。否决。
- **令牌桶**：按匀速补充并以满桶起步，窗口边界能放出接近 2 倍。`100/min` 的语义是「任意 60 秒内不超过 100」，令牌桶不满足这个语义。否决。
- **自设总闸**：官方总量口径是每个出口 IP 1000/min，不是自设值。自设总闸无法与同机其他 Torn 工具协调，同机跑着别的工具时窗口会被别人消耗。否决。
- **把配额塞进每个用途插件**：查询、播报、管理面板各持一份，全局额度被复制 N 份。否决——共享层（`tornapi`）持有窗口，用途插件只调用。

## Consequences

- **多分片部署时内存窗口会按进程复制**，全局额度随之翻倍。届时必须按分片均分预算，或把窗口移到共享存储。当前由单实例锁保证只有一个进程，内存实现是正确的；这是「现在不做分布式限流」的显式前提，不是遗漏。
- **出站层的域名分桶放宽了单域名速率**：配错会打爆上游。因此默认值必须保守、零或负数必须回退并告警、启动日志必须打印实际生效的清单。这条约束写在代码注释之外，也写在这里，因为它是运维事故的唯一预警面。
- **同域名下的多个插件共享同一个桶**（查询与播报不各算一份）。这是「份额度放在出站层」的直接理由；克隆客户端时只复制视图，不复制桶。
- **缓存 key 必须包含 key 的 owner 与作用域**（公开 / 按用户）。部分端点的响应随 owner 变化，缺 owner 会让一个用户的私有数据被另一个用户命中。
- **业务端点超时可按请求放宽**（参考实现取 30 s），走「返回新客户端」的方式，不修改共享实例——放宽一个请求不能顺带改掉全局默认。
