# 会话原语按 peer 独占、一次性消费，落点在 per-peer 串行队列

`Plugin.Handle` 返回 `(*Reply, error)`，事件的生命周期到此结束。要做多轮交互（"发图前先问尺寸""确认后删除"），插件只能自己用 `Host.PeerKV(peer)` 存状态，再注册一个不带 `Commands` 的插件（`matchCommands` 返回 `nil, true`）接住该 intent 的全部消息，最后在 `Handle` 里查 KV 判断"这是不是给我的答案"。这套写法有三个绕不过去的后果：**等待期间无法独占输入**（路由是静态的，等待中的插件 priority 低就被命令插件抢走答案；为了不被抢而提到最高，就会吞掉所有人的所有消息）；**每个需要交互的插件都要重写一遍状态机**（键名、TTL、并发、清理、`/reset` 后的残留全靠自觉——`PeerKV` 只解决了存储隔离，没解决"谁来接这条消息"）；**无法表达"这一步只接受这个人的回复"**（`Handle` 拿到的 `Event` 已是全集，判断条件散落在各插件里）。

本 ADR 定的是：核心持一张 `sessions` 表，键是 peer，同 peer 同时只允许一个插件持有；持有者登记"该 peer 的下一条消息给我"，核心在路由阶段先查这张表，命中就把消息直接投给持有者并删行；登记、拒绝、过期、清理的语义与落点全部写死，插件侧只多一个 `Host.Session().Await`。会话是**数据**（一行），不是控制流。

## 决策

1. **键是 peer，同 peer 同时只有一个持有者。** peer 是群 openid 或用户 openid，不是 `userId+plugin`，也不是全局。nonebot 的 temp matcher 缺的正是这一层隔离（见下节）；按 `userId+plugin` 分键等于"每个插件各占一把锁"，同一会话里两个插件都在等，谁先拿到下一条消息仍然没定义。实现上主键是 `sessions.peer`，另加一列冗余的 `scene`：它**只**用于观测与消费时校验——群 openid 与用户 openid 是两个平台命名空间，万一取值相同，单聊消息不得消费群会话。`scene` 不参与主键，是为了让"一个 peer 一个持有者"这条语义不被复合键悄悄改掉。

2. **一次性消费，不提供可续期标志。** 一次投递即结束，等价于 `temp=True`。多步交互的正确写法是在 `Handle` 里**再次** `Await`：每一步都是"登记下一步"，而不是"延长当前这一步"。不做续期标志的理由是它会让每条消息都刷新过期时间，等于造出一把永不过期的枷锁，而"谁有权延长"这件事没有任何判断依据——用户每说一句话就自动延期，那 TTL 就只是装饰。

3. **消费发生在投递之前：先删行，再调 `Handle`。** 顺序不可交换，有两个不可替代的理由：① `Handle` 内再次 `Await` 写入的新行不会被自己的清理删掉（先投递后删行，第二步会话会在投递返回时被顺手抹掉，表现为"第二步永远等不到答案"）；② 插件 panic 或 3 秒超时也不会留下可供第二条消息消费的行——单次投递的失败不该让会话状态继续存在。代价是 `Await` 之后、`Handle` 返回之前进程被强杀时这条会话会丢，这是一次性语义的固有性质，不做补偿。

4. **过期时间：默认 5 分钟，上限 1 小时。** `ttl <= 0` 取 `DefaultSessionTTL`；`ttl > MaxSessionTTL` 截到 1 小时——**截断而不是报错**，因为 TTL 是策略不是逻辑，插件算错一个数不该让整条链路失败。语义上"过期"等于**行不存在**：读路径发现 `expires_at <= now` 就删行并落回静态路由（不需要额外的 `expired` 状态位），GC 每 10 分钟兜底清一次过期行。写路径同样把过期行当作不存在——`Await` 遇到一个过期行不算冲突，直接替换。

5. **同 peer 已被占用 → 拒绝，不覆盖。** 返回哨兵 `host.ErrSessionBusy`，由插件决定提示用户还是安静放弃。覆盖会让先来的插件被静默饿死：它在等一条永远不会来的消息，日志里什么都没有。两个例外必须写明：① 持有者**是调用者自己** → 覆盖，同一插件对同一 peer 重复 `Await` 就是"改 state、重新计时"，此时保留 `created_at`，只更新 `state` 与 `expires_at`；② 持有者**已不在加载集合**（插件卸载或重载后从路由表消失）→ 当作悬挂会话直接替换，否则新插件会被一个永远不会有人消费的行永久挡住，且用户只有等 5 分钟过期才能重来。

6. **路由顺序与落点是硬约定。** 顺序：闸门 → 去重 → 群生命周期 → 权限视图（`Actor`）→ 核心保留指令 → **会话接管** → 静态匹配。只对 `KindMessage` 生效；notice、群生命周期、未知事件一律不消费会话——它们不是"用户说的话"，拿它们推进会话等于把平台通知当成答案。

   落点必须写清是 **`Dispatcher.handle` 内**（同一 peer 的串行队列里），**不是** `Core.Handle`。评审稿 §2.1 写的"`handleReserved` 之后、`dispatch.Dispatch` 之前"在实现上会绕过 per-peer 串行队列：`Dispatch` 只做入队，`handle` 才在队列协程里跑，在 `Core.Handle` 里查会话会让会话推进与静态路由并发打到同一个 peer，破坏"同 peer 串行"这条硬保证（`msg_seq` 单调、插件不对同一用户并发查询，都靠它）。这是与评审稿的**有意偏差**，留档以免日后被当成实现错误"修正"回去。

   注意队列键是 `scene + ":" + peer`（`dispatch.go:61`），而会话主键只有 `peer`，两者差一层 scene。这不是漏洞：跨场景的消息落在不同队列，但同一行会话只会被 `scene` 匹配的那条消费，所以"能消费同一行的消息"仍然严格串行。

7. **权限先于接管。** 会话投递用的是持有者的 `Manifest.Permission`——会话消息没有命令，因此没有 `Command.Permission` 可用。无权限 → **不消费**（不删行）、轨迹记一行「权限不足」、消息落回静态路由。不能吞掉这条消息：一个群里普通成员说的话在管理员插件等待期间被无声吃掉，是比"多回一条"严重得多的故障；也不能删行，否则一次越权尝试就能把管理员的会话顶掉。

8. **会话接管不检查 `Manifest.Intents`。** 静态路由会按 intents 过滤候选，会话接管不会：持有者是**显式**要求这条消息的，`Await` 那一刻就已经声明了"这个 peer 的下一条消息归我"。要求插件额外声明 `message` intent 只会制造一类"登记成功但永远收不到"的静默故障。

9. **插件卸载 / 重载留下的是悬挂会话，在消费时清理。** 消费时发现持有者不在路由表 → 删行 + `warn` + 该消息落回静态路由，不静默吞掉。**不在启动期批量清理**：全表扫没有收益（行数是个位数），而下一条消息必然会触发清理，多写一个启动期扫描只是多一处会失败的地方。

10. **`/reset` 分级要跟着这张表走。** R1 清该 peer 的 `sessions`；R2 一并清该 peer 的 `sessions`（清数据等于"这个会话重新开始"，挂着一个等输入的会话是荒谬状态）；R3 清全表；R0 不动。R1 必须清的理由很直接：不清就等于"重置完留下一个永远等不到输入的悬挂会话"——用户的下一步输入会被一个已经忘记上下文的插件接管，比直接不响应更难排查。

11. **可观测性不能省。** 会话是**隐式路由**：消息没有命中任何命令就被某个插件拿走了，静态匹配的那套轨迹（命中 / 未命中 / 未让位）全都不适用。三处必须补：① 会话投递时打一行独立的「会话接管」轨迹，`full` 与 `plugin` 两个级别都打——`plugin` 级别回答的正是"谁触发了我"，而这行是唯一答案；② `/group status` 显示该群的会话持有者与剩余时间；③ `/group status` 的私聊总览显示进行中的会话数（有多少 peer 处于会话中）。

12. **Host 契约形状：取能力，不往 `Host` 上挂方法。** 与 `Sender()` / `KV()` / `Renderer()` 的访问器风格一致：

    ```go
    type Session interface {
        Await(ctx context.Context, ev *Event, state []byte, ttl time.Duration) error
    }
    ```

    没有 `Host.Await(...)`：那会让 `Host` 每加一项能力就膨胀一个方法，而现有风格是"一项能力一个访问器"。哨兵与常量放在 `host` 包，不放在实现包里——插件只 import `host`，哨兵放在实现包，插件的 `errors.Is` 永远拿不到它（理由同 `render.go` 的 `ErrRenderTooLarge`）：`ErrSessionBusy`、`DefaultSessionTTL = 5 * time.Minute`、`MaxSessionTTL = time.Hour`、`MaxSessionStateBytes = 8 << 10`。`state` 超限**直接报错，不许悄悄截断**——截断的 JSON 是坏数据，插件下次读到它只会得到更难查的错。

    回应如何识别：`Event.Session *SessionContext`，`SessionContext{Plugin string; State []byte}`；非 nil 表示这条消息是对本插件 `Await` 的回应，此时 `Command` / `Args` 恒为空（会话响应不是命令）。`Await` 只能从 `Handle` 里调用——它必须有一个 inbound 事件提供 peer 与 scene，从定时任务或 `Init` 里发起没有这个前提。

13. **契约版本 = 9。** 当前是 8（`internal/host/host.go`）。新增 `Host.Session()` 与 `Event.Session` 都是破坏性变更：`Host` 是接口，加方法会让所有自实现 `Host` 的测试替身编译失败；`Event` 加字段对插件是兼容的，但版本是整体匹配，不为一个字段单独立版本。

## `sessions` 表

```sql
-- 会话接管（ADR-0004）。一行 = 一个 peer 当前被某个插件占用。
-- 主键只有 peer：同 peer 同时只允许一个持有者，场景不参与"谁能接管"的判定。
CREATE TABLE sessions (
  peer       TEXT PRIMARY KEY,          -- 群 openid 或用户 openid
  scene      TEXT NOT NULL DEFAULT '',  -- group | c2c；只用于观测与消费时校验，不参与主键
  plugin     TEXT NOT NULL,             -- 持有者：投递目标、权限来源、悬挂判定
  state      BLOB NOT NULL,             -- 插件自定义字节（建议 JSON），≤ 8 KiB
  created_at INTEGER NOT NULL,          -- 接管时刻：排障用，不参与过期判定
  expires_at INTEGER NOT NULL           -- 过期时刻；读路径据此判"行不存在"
);
CREATE INDEX idx_sessions_expires ON sessions(expires_at);
CREATE INDEX idx_sessions_plugin  ON sessions(plugin);
```

每一列的存在理由：

- `peer` 是主键，也是唯一的冲突判定依据。不加 `plugin` 进主键，因为"同 peer 两个插件同时等"恰恰是要拒绝的状态，而不是要容纳的状态。
- `scene` 冗余存在，是因为群 openid 与用户 openid 来自两个平台命名空间，取值域不保证不相交。消费时校验 `ev.Scene == sessions.scene`，不匹配则不接管、不删行、落回静态路由。把它放进主键会得到 `(scene, peer)` 两个持有者，直接推翻决策 1。
- `plugin` 列承担三件事：投递目标；取 `Manifest.Permission` 判权限（决策 7）；判断持有者是否还在加载集合（决策 5 的例外②、决策 9）。
- `state` 是插件自己的字节，核心只做长度检查与转发，不解释内容。列名与 `plugin_kv` 的 `peer` 语义一致——两者都表示**会话维度**，不是插件维度：`plugin_kv.peer=''` 是插件级全局键，而 `sessions` 没有"全局会话"这种形态，`peer` 恒非空。
- `created_at` 只用于观测（"什么时候接管的""等了多久"）。过期判定只看 `expires_at`，避免两列在同一语义上打架。
- `expires_at` 同时服务读路径判定与 GC。索引是为了让每 10 分钟的 `DELETE ... WHERE expires_at <= ?` 走索引而不是全表扫。
- `idx_sessions_plugin` 的唯一用途是排障查询（插件重载后核对"它留下了哪些行"、`/group status` 之外的按插件统计），不参与热路径。可观测性在决策 11 里是硬要求，这个索引是它的查询入口。

## 与 nonebot temp matcher 的差异

nonebot 的 `pause()` / `reject()` / `finish()` 是**抛异常终止 handler 链**，`run()` 顶层捕获后用 `Matcher.new()` 重建一个 temp matcher（`temp=True`、`priority=0`、`block=True`、`default_state=self.state`、`expire_time`）。行为上确实做到了"下一条消息接着走"，但实现方式与本项目的硬约束逐条冲突：

| 维度 | nonebot temp matcher | 本实现 | 为什么不能照抄 |
|---|---|---|---|
| 会话的表示 | 异常控制流 + 重建 matcher | 一行数据（`sessions`） | 异常控制流要求 `Handle` 有能力"中止整条链"，Go 里只能靠 panic 或返回哨兵错误，两者都会污染所有插件的错误语义 |
| 生命周期 | 进程内存，重启即失 | SQLite 持久化 | 重启后用户的"下一步"仍在等；内存实现还会让 `/reset` 清不掉（进程内 map 不在任何重置路径上）、多进程不一致 |
| 优先级 | `priority=0` 抢在所有插件前面 | 由核心**显式**接管，不参与 priority 排序 | priority 0 只是"排序第一"，同 priority 的插件仍有竞争；而且它会一并抢走命令消息（用户想 `/reset` 也会被吞），所以 nonebot 需要 `block=True` 与各种 updater 兜底 |
| 独占 | `block=True` 阻止向下传播 | 接管即跳出静态匹配 | 本实现不需要这个标志：命中会话就不进静态路由，"独占"是结构性结果而不是一个可配开关 |
| 多轮 | `reject()` 重放当前步 / `pause()` 从下一步继续 | 两种都写成"在 `Handle` 里再次 `Await`" | 重放与续跑的区别只体现在插件是否重读 state，核心不为此分裂出两个原语 |
| **隔离** | 重建时 `rule=Rule()`、`type="message"`，**不比对 `session_id`** | peer 写进主键 | nonebot 里 pause 之后**任意用户**的下一条消息都能推进这个会话，隔离要靠插件的 `type_updater` / `permission_updater` / `set_target` 自己维护，在活跃群里是实际会串的。这是最需要留档的一条：任何"照抄 nonebot"的改动都会把这个缺陷一起带进来 |

最后一行是本 ADR 存在的核心理由。会话的**身份**必须在核心的数据模型里（`peer` 主键），不能靠插件的 updater 自觉——只要有一处忘了写，串话就发生了，而且没有任何报错。

## Considered Options

- **进程内 `map[peer]*session`**：省掉每条消息一次查询，但重启即失（用户正在进行的对话凭空消失）、`/reset` 清不掉（map 不在任何重置路径上，只能加一条"顺便清内存"的旁路，而旁路总有漏的）、多进程不一致（两个进程各持一份，谁接管取决于消息投到哪个进程）。持久化是"重置分级"与"重启续跑"两个需求的交集，绕不过去。否决。
- **复用 `plugin_kv` 存会话**：核心要往插件命名空间里写行（插件一 `DeletePrefix` 就把会话抹了），要按前缀代表会话还需要全表扫或额外索引，而且 `plugin_kv` 的主键是 `(plugin, peer, k)`——**加不进 `peer` 唯一约束**，没法用一条 `INSERT` 表达"同一 peer 只允许一个持有者"，只能先查后写，两个并发 `Await` 都能通过检查。主键点查 + 唯一约束是这张表存在的全部价值。否决。
- **`Await` 直接挂 `Host`（`Host.Await(...)`）**：少一个接口，但 `Host` 会随每项能力膨胀一个方法；现有风格是访问器（`Sender()` / `KV()` / `Renderer()`），测试替身也因此能按能力单独注入。否决。
- **同 peer 已占用时覆盖**：实现最省事，但先来的插件在等一条永远不会来的消息——没有错误、没有日志、没有超时，只有用户觉得"机器人有时候不理我"。拒绝 + `ErrSessionBusy` 至少把"谁该让"的决策交回给知情的一方。否决。
- **在 `Core.Handle` 里接管**（评审稿 §2.1 的原始写法）：落点在入队之前，会话推进与静态路由会并发打到同一个 peer，`msg_seq` 单调与"插件不对同一用户并发查询"这两条保证同时失效。改动一行位置就能避免，没有理由留这个坑。否决。
- **可续期标志（`refresh` / `extend`）**：每条消息都刷新过期时间，等于永不过期；而且"谁有权延长"没有判断依据——用户说话就算延长，那 TTL 只是装饰；插件主动延长又回到"忘了延长就丢状态"的老问题。否决。
- **用 priority 0 的无命令插件占位**（照抄 nonebot 的现状，也是当前的手工做法）：不需要新契约，但 priority 0 只是排序第一，同 priority 仍有竞争；它会连命令消息一起吞掉（用户敲 `/reset` 也进不了核心——除非核心保留指令硬编码在最前面，那又变成"某些消息特殊、某些不特殊"的隐式规则）；状态机仍然每个插件重写一遍。否决。

## Consequences

**正面**：多轮交互从"每个插件自造一套"变成一个核心原语；会话在重启后仍在，`/reset` 清得掉，插件卸载不会留下永久占位（消费时清理，与 `Await` 时发现持有者已不在加载集合就替换，两条路径都覆盖了）；会话推进天然落在 per-peer 串行队列里，不需要额外加锁；插件侧只多一个 `Await` 调用，不需要 `pause` / `reject` 这类控制流。

**代价（都要认）**：

- **每条消息多一次主键点查**（SQLite 上约 1–2 µs）。不做内存"有无会话"快速判断：那需要在每条写路径上同步维护一份内存索引，而正确性只在"持久化行"这一个事实源上，缓存只会引入"内存说有、库里没有"的分歧。先量再优化——如果压测显示它真的进了热路径，再考虑按 peer 缓存，而不是现在为假想问题加一层需要保持一致性的状态。
- **新增一个用户可见概念**（"会话接管"）。文档、轨迹、`/group status` 三处都得覆盖，否则使用者会遇到"机器人为什么不理我"而查不到任何线索。本 ADR 与 §3.2 / §3.3 / §3.4 / §8.3 的同步改动就是这个代价的预付。
- **`ErrSessionBusy` 把"谁该让"交回插件**：插件可能选择报错打扰用户（"请先完成上一个操作"），也可能选择安静放弃（用户完全不知道发生了什么）。核心不替它决定，因为只有插件知道自己的会话是否可被打断。
- **持久化意味着 state 格式必须向后兼容**：写进去的是插件自己定义的字节，进程重启后仍在等；插件升级时改了 JSON 结构，就要自己处理旧格式（或显式放弃并发一条提示）。核心不解释、不迁移、不校验 state 内容。
- **过期等于行不存在**，所以读路径带一次写（`DELETE`）。这是"不想多一个状态位"的直接代价：读热点上会出现少量写，好在会话行极少、且只在 `expires_at` 已过的行上发生。
- **一次投递即删**：`Await` 之后、`Handle` 返回之前进程被强杀的会话会丢。不做补偿（补偿需要把"正在投递"也持久化，收益远小于复杂度）。

## 本 ADR 不做

- **可续期标志**（决策 2 已给理由）。
- **多步并发会话**：一个 peer 同时只能有一个待处理步骤。要并行推进两条对话，得用两个 peer 或插件自己的 KV。
- **跨 peer 会话**：一个 `Await` 只绑定一个 peer；"等群里任意一个人回答"要靠插件的静态订阅，不靠会话。
- **会话内嵌套会话**：`Await` 覆盖同一行，不建栈。
- **会话消息的 `Command` / `Args`**：恒为空。会话响应不是命令，把原文塞进 `Command` 会让插件写出依赖"上一步的命令"的隐式状态。
- **从定时任务或 `Init` 发起 `Await`**：只能从 `Handle`（需要 inbound 事件提供 peer 与 scene）。
- **state 加密或校验**：核心不解释内容，长度上限是唯一的检查。
- **多实例共享会话**：单实例锁（§2.1）保证只有一个进程；将来多分片时这张表要跟着分片走，不在本次范围。
