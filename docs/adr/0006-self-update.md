# 自更新：按需检查、双通道校验、核心与插件不对称回滚

现在的升级流程是 §9.2 写的两步：停进程、换二进制、`systemctl restart`。对小规模自用够用，但它要求能 SSH 到机器；一旦机器在别人手里（"你 + 少数朋友"的分发形态），每次发版都变成一次人工操作。而 ADR-0005 之后插件已经是独立产物，插件更新更不该要求登录服务器。

本 ADR 定的是：`/upgrade` 是**唯一**的更新入口，只在人主动敲的时候发请求；元数据与校验和从一个通道取、二进制允许从镜像取；核心的回滚要带 DB 快照而插件的不需要，两者**刻意不做成同一套机制**。

## 决策

1. **只在 `/upgrade` 时检查，启动期不查。** 不做"启动时静默检查 + 日志提示"：那会引入一个没人看的日志行、一次可能失败的开机网络请求，而且真发现了也不会有人知道——因为没有主动通知的通道（私聊 owner 要吃主动消息日预算，把升级信息塞进 bootnotice 又等于让核心给插件传业务，违反"插件不知道核心有升级这回事"）。要更新就敲一条命令，代价小得多。

2. **命令面四段，owner-only，不加确认码。**

   | 命令 | 行为 |
   |---|---|
   | `/upgrade` | 检查并预览：当前版本、最新版本、插件升/跳过清单、产物大小。**不改动任何文件** |
   | `/upgrade apply` | 应用核心升级：快照 → 下载 → 校验 → 落位 → 重启 |
   | `/upgrade plugin [name\|all]` | 应用插件升级，直接生效（回滚几乎免费，见决策 6） |
   | `/upgrade status` | 当前版本、是否有未确认的升级、上次失败原因 |

   不加 6 位确认码的理由：码是防越权的（`/reset` R2/R3 那类不可逆数据操作），而这里已经有 owner 权限加一次显式 `apply`，"预览 + 二次命令"本身就是确认。

3. **元数据与二进制分两个地址。**

   ```toml
   [upgrade]
   enabled     = true                              # 关掉之后连检查都不发请求
   api_base    = "https://api.github.com"          # 元数据 + checksums.txt
   asset_base  = "https://github.com"              # 二进制；可指向镜像
   ```

   `checksums.txt` **永远从 `api_base` 取，不从 `asset_base` 取**。这条把"校验和与二进制不同通道"从一个约定变成结构约束：镜像站被投毒时二进制变了、校验和没变，必然对不上。没有这条，SHA-256 只能防传输损坏。

4. **校验只比 SHA-256，不引入签名。** 明确它覆盖什么：传输损坏、截断、镜像站投毒（决策 3 的前提）。**不覆盖**上游仓库或账号被 takeover——那种情况下攻击者能同时改二进制与 `checksums.txt`。接受这个残余风险的理由是当前分发范围（自用 + 少数朋友，私有仓），而不是认为签名没价值；将来若对公众发布，补 ed25519 签 `checksums.txt` 是增量改动，不动本 ADR 的其他决策。

5. **落位：同卷临时文件 + fsync + rename，不跨卷。** 下载写在目标文件的同目录（`<exe>.new`），否则 `rename` 会退化成"复制 + 删除"，既慢又不原子。Unix 还要 `fsync` 目录项；Windows 没有目录 fsync，靠 `MoveFileEx` 的语义。

   - **Unix**：`link(exe, exe.old)`（硬链接，秒级、不复制 40 MB）→ `rename(exe.new, exe)` → `exec`。`exec` 失败时进程还活着，可以 `rename(exe.old, exe)` 原地回滚再 `exec` 一次——同步错误在进程内就能收住。
   - **Windows**：运行中的 exe 不能覆盖或删除，但**可以改名**（镜像以 `FILE_SHARE_DELETE` 打开）。顺序是 `rename(exe, exe.old)` → `rename(exe.new, exe)` → spawn → 退出；`.old` 留到下次启动再删，失败只 `warn`（可能被旧进程或杀软短暂持有）。

6. **回滚刻意不对称。**

   - **核心**：升级前写 `<datadir>/upgrade/state.json`（目标版本、旧文件路径、尝试次数），并对 DB 做 `VACUUM INTO` 快照。启动时若发现 pending：尝试次数 +1；`> 1` 就还原 `exe.old` 并对自己再 `exec`/spawn 一次，日志用 Error 级别写清原因。**启动成功 = `core.Start` 完成且网关协程存活 30 秒**，之后删标记。用"存活 30 秒"而不是"网关连上"：网络抖动不该触发回滚，而一个连不上网关的版本通常也是网络问题。
   - **插件**：无状态、无迁移，回滚就是"把旧文件换回来、重启子进程"。新进程 5 秒内没完成 `init` 握手 → 自动换回旧文件重启，静默成功就只记一条 Warn。

   把插件也套上 pending 标记 + 快照，只会让"换个插件"背上"换核心"的重装备。

7. **核心升级时 `plugins/bin/` 只升不降。** 内嵌副本是出厂态，远端 `index.json` 是版本事实源；落位时逐个比较，**只替换版本更高的**，跳过的写进升级报告。覆盖会把用户单独升过的插件静默降级；原样保留则内嵌的新版本永远装不上。

8. **复用现有重启序列，不新造一条。** `/upgrade apply` 的结尾就是 `/reload` 已经做对的那条路：先回消息（被动窗口重启后就不存在了）→ 关网关并把 `session_id`/`seq` 落盘 → `core.Shutdown` → 关库 → 换盘 → `exec`/spawn。升级不额外动 session，重启后走 Resume，不烧 Identify 配额（§9.2）。

9. **`Version == "dev"` 时拒绝自更新。** `dev` 无法参与版本比较，`-ldflags` 注入是发布版本号的**唯一**来源。这条顺带挡住一类事故：本地 `go build` 出来的二进制混进生产，然后 `/upgrade` 试图把它"升"到某个正式版本。

10. **`/upgrade` 进核心保留前缀清单。** 现为 `/claim /admin /group /reset /reload /restart`；清单与 `handleReserved` 的对应关系有测试锁住，加它要一起改。插件占用同名指令仍按现有规则拒绝加载。

11. **发布产物形状**（CI，非运行期）：

    ```text
    qqbot-<version>-windows-amd64.exe
    qqbot-<version>-linux-amd64
    qqbot-<version>-linux-arm64
    checksums.txt          # sha256，覆盖以上全部
    plugins/index.json     # 插件版本与资产清单（含各平台的 sha256）
    ```

    构建顺序固定：先编插件到 `dist/<os>_<arch>/`，再编核心（`go:embed` 依赖它们），最后跑 `sha256sum`。版本号只经 `-ldflags -X .../buildinfo.Version` 注入，`commit` 仍由 Go 自动嵌入的 VCS 信息提供。

## 为什么下载不走 `httpx`

`httpx` 是插件出站通道：只解 JSON、`maxBodyBytes = 8 MiB`、域名额按业务计。40 MB 的产物用不了它，也不该占用插件的配额桶。核心自带一个极小的流式下载器（`io.Copy` 到临时文件 + 长度与 sha 边写边算），只有它认识 `api_base`/`asset_base`。这条写进 ADR 是为了防止后来者"复用现成的 HTTP 客户端"而把 8 MiB 限制带进升级路径。

## Considered Options

- **启动时检查 + 私聊提醒**：体验最好。但吃主动消息日预算，且需要一条"升级可用"的状态穿到插件层——正好是 ADR-0005 决策 14 想避免的那种耦合。否决。
- **一条 `/upgrade` 直接检查并应用**：少一次交互。但"看一眼会发生什么"和"现在就开始换二进制"是两种意图，合并后 owner 在群里手滑就触发一次 40 MB 下载加重启。否决。
- **加 6 位确认码**：与 `/reset` 一致。但 `/reset` 的码防的是"不可逆的数据删除"，这里改动可回滚，且已有 `apply` 作为第二道动作。否决。
- **ed25519 签名 `checksums.txt`**：能防上游被 takeover。当前分发范围不需要，且它引入一份必须离线保管的私钥与一套 CI 签名步骤。留作增量（决策 4）。
- **外部 supervisor 负责回滚**（把 `tools/devrun` 那套推到生产）：能覆盖"新版本反复崩溃"这类 pending 标记覆盖不到的形态。但要求服务器上有源码与工具链（`go generate` + `go build`），与"单文件分发"直接冲突。否决。
- **核心与插件共用一套回滚机制**：代码更少。但核心需要 DB 快照与"启动成功"的判定，插件两者都不需要；共用会让插件升级继承一堆它用不上的状态机。否决。
- **`plugins/bin/` 每次核心升级都按内嵌副本覆盖**：实现最简单。但会静默降级用户单独升过的插件，且升级报告失真。否决。

## Consequences

**正面**：不用 SSH 就能升级，插件尤其如此（它现在有独立的升级粒度）；升级后走 Resume，不额外烧 Identify 配额；版本可核对（`/ping` 对比 version + commit，bootnotice 报上线）；核心回滚有 DB 快照兜底，插件回滚成本接近于零；`api_base`/`asset_base` 分离让镜像站从"风险"变成"可用选项"。

**代价（都要认）**：

- **升级通道就是远程代码执行通道。** 服务账号能改自己的二进制，任何 RCE 都会变成持久化。这是自更新的固有代价，只能靠"owner-only + 校验 + 私有源"缓解，不能消除。部署上还要配套：把二进制装进可写目录（`/var/lib/qqbot/bin` 并改 `ExecStart`），或给 `/opt/qqbot/bin` 加 `ReadWritePaths`——后者等于放开 `ProtectSystem=strict` 的一部分。
- **`VACUUM INTO` 要磁盘与时间。** 库大时快照会明显变慢，需要保留最近 2 份并定期清理，否则升级路径本身会变成磁盘增长的来源。
- **DB 迁移与回滚冲突。** 回滚二进制不等于回滚 schema，所以安全回滚窗口只有一个版本，且要求迁移只增不减。跨破坏性迁移时，回滚必须配快照还原（人工）。
- **Windows 特有故障**：杀软扫新写入的 exe 会让 `rename` 间歇失败，必须重试并给出可读的错误；`.old` 清理失败会长期留一份 40 MB 副本。
- **多一个配置段与一类新的失败模式**（网络不可达、镜像不同步、校验不通过、`index.json` 与产物不一致）。每一条都要有明确的用户可见文案，否则 owner 只会看到"升级没反应"。

## 本 ADR 不做

- **签名**（决策 4，增量）。
- **多通道 / 灰度 / 自动回滚到指定版本**：只有"最新"一个目标。
- **离线升级包**（`qqbot upgrade --from-file`）：手工替换二进制本来就是这条路，不需要额外的命令。
- **插件市场**：`/upgrade plugin` 只处理 `index.json` 里列出的插件。
- **系统级安装脚本**（systemd unit 的生成与安装）：`deploy/qqbot.service` 仍是手工放置。
